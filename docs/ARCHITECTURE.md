# Как устроены сервисы KinoKrad и Kinogo

Документ описывает внутреннюю механику: что делает сервер, зачем ему браузер, как получается
подписанная ссылка и почему видео идёт через сервис, а не напрямую с CDN.

## Общая схема

```
                 ┌──────────────────────── сервис (aiohttp) ───────────────────────┐
Lampa на ТВ ───▶ │ /api/search   →  HTTP-клиент (curl_cffi)  →  каталог источника  │
                 │ /api/detail   →  карточка + список серий/озвучек                │
                 │ /api/resolve  →  Chromium: подпись потока у плеера источника    │
                 │ /hls, /p, /media →  прокси плейлистов и сегментов к CDN         │
                 └────────────────────────────────────────────────────────────────┘
```

Ключевая идея: телевизор не должен повторять защитную логику источника. Он получает обычный
HLS, а всё неудобное (TLS-отпечаток, подпись, заголовки, CORS) делает сервер.

## Поиск и карточка

- **Поиск** — обычный HTTP-запрос к тому же AJAX-эндпоинту, которым пользуется сайт
  (`curl_cffi`, отпечаток Chrome, keep-alive). Тяжёлая страница каталога не загружается.
- **Карточка** — HTTP-запрос страницы тайтла и разбор структуры (`parsers.py`): название, год,
  постер, описание, сезоны/серии и список озвучек с их `file_id`/`translation_id`.
- **Второй плеер** (`provider=backup`) — отдельная штатная вкладка сайта; сервер читает её
  метаданные, строго выдерживает запрошенные сезон/серию и отдаёт свой HLS.

Для KinoKrad вызовы идут через `curl_cffi` с TLS-отпечатком Chrome; если сайт начинает
отвечать защитным 403/404, сервис переходит на резервный путь через браузер.

## Подпись потока

Плеер источника выдаёт HLS только с динамической подписью, которую создаёт защитный
браузерный слой (в KinoKrad это «Borth», в Kinogo — дерево плейлиста Cinemar).

Поэтому сервис:

1. держит **один постоянный Chromium** (Playwright), а не запускает браузер на каждый запрос;
2. прогревает страницу плеера при открытии карточки, чтобы к нажатию «Смотреть» всё было готово;
3. переключает серию/озвучку **меню самого плеера**, а не перезагрузкой страницы;
4. забирает из браузера готовые заголовки и ссылку, после чего кэширует результат на время
   жизни потока (`STREAM_TTL`);
5. при истечении подписи обновляет её через тот же штатный загрузчик (`loadSource`/`startLoad`),
   не смешивая сессии разных серий.

Подпись одноразовая и короткоживущая: две подписи в одну секунду источник может отклонить,
поэтому шаги меню разведены паузой (`SIGN_GAP`).

## Отдача видео

Сервис переписывает плейлисты на себя:

```
master:  #EXT-X-STREAM-INF …        variant:  #EXTINF:6.0,
         /hls/<key>/<audio>/720.m3u8          /p/<key>?u=<абсолютный URL>
```

- **сегменты** отдаются с прозрачной передачей `Range` — перемотка и `206 Partial Content`
  работают как обычно;
- **заголовки источника** (`Referer`, `User-Agent`, cookies подписи) подставляет сервер:
  из браузера телевизора их отправить нельзя;
- **allowlist доменов** не даёт превратить прокси в открытый релей: разрешены только CDN
  источников;
- **упреждающая загрузка** (`PREFETCH_AHEAD`, `SEGMENT_PARALLEL`, `SEGMENT_CACHE_MB`) держит
  буфер впереди плеера, иначе ускоренное воспроизведение упирается в CDN.

## Маршруты в сеть

Видео и каталог могут ходить разными путями. Если источник нестабилен, задайте единый выход:

- `KK_UPSTREAM_PROXY` — основной HTTP-прокси для Chromium и запросов к CDN;
- `KK_FALLBACK_PROXY` — резервный, сервис переключается на него при блокировке;
- `KK_FORCE_ROUTE=vpn|direct` — принудительный маршрут для диагностики (снять после проверки).

Важно: при смене маршрута старая сессия источника инвалидируется. Сервис в этом случае
перезапускает браузер и делает свежий resolve, а не переиспользует мёртвую сессию.

## Kinogo

Отдельный сервис (`kinogo/`) с той же идеей, но своим источником и плеером (Cinemar):

- каталог и карточки — HTTP + `article.shortStory`;
- дерево плейлиста разворачивается в браузере штатным клиентом Cinemar, сервер выбирает
  **точный** `pjs_id` запрошенной серии, а не «первую попавшуюся»;
- медиа идёт через `/media?u=…` с тем же правилом: плейлисты переписаны, сегменты с `Range`;
- при TLS/сетевой ошибке зеркала сервис берёт другое зеркало из того же подписанного дерева;
  4xx так не обходятся — это честная ошибка источника.

## Что означают ошибки

| Симптом | Вероятная причина | Что смотреть |
|---|---|---|
| `manifestLoadError` | master/variant не получен | лог сервиса: `resolve`, `/hls`, `/p` |
| `fragLoadError` | сегменты рвутся | `SEGMENT_*`, маршрут в сеть, скорость |
| 403/WS4005 при resolve | сессия не подписана | `KK_FORCE_ROUTE`, резервный прокси |
| пустые `audios`/`tracks` | отфильтрованы allowlist'ом | список разрешённых CDN-хостов |
| `bufferAppendError` на ТВ | декодер телевизора | полный перезапуск Lampa/MSX |

## Производительность

- поиск и карточка не поднимают браузер — это единицы миллисекунд на локальной сети;
- первый запуск серии стоит один проход браузера, дальше серия/озвучка переключаются меню
  уже прогретой страницы;
- одинаковые параллельные запросы схлопываются (single-flight), поэтому двойное нажатие
  на пульте не создаёт две подписи.
